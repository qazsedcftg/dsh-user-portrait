# 人物画像 · User Portrait

> 一个 DSH Host/Client 双向插件：把你在每次会话里**提出的内容**自动提炼成一份结构化、可审阅、可纠正的「人物画像」，并在新会话里**按需**提供给模型。

[English](./README.md) · 中文

- 包名：`dsh-user-portrait`
- 入口：`index.js`（Host 半边）、`client.js`（Client 半边）
- 画像数据：`<DSH_HOME>/user-portrait/`（未设置 `DSH_HOME` 时为 `~/.dsh/user-portrait/`；可用 `dataDir` 覆盖，默认留空）
- 面板入口：右栏「人物画像」标签页 · 会话头部「画像」按钮 · 设置 →「人物画像」

## 安装

```powershell
# 普通 dsh web 环境
dsh plugin --profile web add dsh-user-portrait

# 桌面版：装精确版本（市场一键安装也是这个形式）
dsh plugin --profile desktop add dsh-user-portrait@1.1.0
```

装好后重启 DSH（或在插件管理器里重载），右栏就会出现「人物画像」页签。不需要构建步骤，也不需要额外依赖。

## 1. 它做什么

| 你当初的要求 | 落地方式 |
|---|---|
| 提取每次会话我提出的内容，构成人物画像 | 每轮结束后台提炼：**我问的 / 要点 / 你答的 / 纠正与偏好**，并抽出带置信度的维度证据 |
| 结构化十来个维度 | **9 个维度、2 个分组**（日常画像 5 + 技术画像 4），按「证据条目」累积，每条带置信度与来源会话 |
| 用简介内容概括我的提问与你的回答留档 | 逐轮摘要（`turns/*.jsonl`）+ 会话整体概要（`sessions/*.json`）+ 人类可读 Markdown（`views/*.md`） |
| 需要时让模型参考画像 | 输入框旁的「画像」开关**按会话**开启后，系统提示注入一小段「画像可用」提示；四个工具始终可用 |
| 使用简介内容概括 | 提示段只给可用性，细节留在工具后面按需读取，避免陈旧结论干扰判断 |
| 完善描绘我 | 冲突时旧条目标 `superseded` 保留、新条目生效；**用户手动纠正与备注优先级最高** |

### 9 个维度（分日常 / 技术两组）

技术侧把相似项合并了：原来分散的 `ability`/`tech`/`domain`/`tooling` 都是「我会什么、用什么」，合并成**能力与技术栈**；`workstyle`/`values`/`decision` 都是「我怎么干活、凭什么取舍」，合并成**工作方式**；`communication` 属于说话方式，归入日常的**性格与沟通**。

**日常画像**（`daily`）—— 只有你亲口说过的才进来，所以条目少、置信度偏低是正常的：

| id | 名称 | 关注点 |
|---|---|---|
| `personality` | 性格与沟通 | 性格倾向、对待反馈的态度、期望的回复详略与结构、语气与术语密度 |
| `interests` | 兴趣与爱好 | 长期兴趣、业余投入、持续关注的话题与内容品类 |
| `background` | 生活与身份 | 身份与专业背景、作息与时间安排、生活层面的固定约束 |
| `focus` | 当前在做 | 正在推进的项目、阶段目标、近期关注点 |
| `current` | 近期状态 | 忙闲节奏、压力来源、正在等待或纠结的事（短期结论，会自然过期） |

**技术画像**（`tech`）：

| id | 名称 | 关注点 | 吸收了旧维度 |
|---|---|---|---|
| `skill` | 能力与技术栈 | 语言/框架/平台熟练度、擅长的任务类型、专业与行业背景、常用工具与编辑器偏好 | `ability` `tech` `domain` `tooling` |
| `workstyle` | 工作方式 | 节奏与粒度、计划性与验证习惯；正确性/效率/可维护性/隐私/成本的优先级；不确定时如何收敛 | `workstyle` `values` `decision` |
| `boundary` | 风险边界 | 不接受的做法、红线、必须先确认的事项、授权尺度 | `boundary` |
| `friction` | 敏感点 | 反复纠正的点、易被误解之处、明确表达过不满的行为 | `friction` |

> **旧数据不会丢**：`profile.json` 的 `version` 已升到 2；读取时会把旧维度的条目**折叠**进合并后的维度（按文本去重），再次读取不会重复折叠。旧 id 仍可作为 `portrait_read` / `portrait_maintain` 的参数传入，会被解析到新维度。

### 面板外观（对齐桌面版官方设计系统）

面板不再用自造的圆角与下划线链接，而是直接采用官方控件的度量与令牌：

| 元素 | 采用的官方规格 |
|---|---|
| 工具栏按钮 | 官方 `Button` 的 `sm` 规格：28px 高、8px 圆角、12px 字；「立即重新提炼」= `primary` 品牌填充，「回填全部历史会话 / 重新提炼全部历史」= `outline` 0.5px 描边，「刷新 / 在设置中打开」= `ghost`，hover 统一 `interactive-bg-hover` |
| 页签条 | 官方 `SegmentedTabs` 的轨道 + 滑动指示器（`bg-module-platform` 轨道、`bg-layer-3` 指示器、0.5px `border-l3`、选中 600 字重） |
| 状态标签 | 官方 `Tag` 几何（17px 行高、11px 字、全圆角），tone 用 `color-mix` 取状态色 10~12% 染色；置信度 高/中/低 = `success`/`warning`/`quiet`，手动 = `info` |
| 行内操作 | 24px 的 icon-button，默认透明、悬停 `bg-layer-4` 并显现；「删除」悬停用 `interactive-bg-hover-danger` + `label-error` |
| 输入 / 下拉 | 官方设置表单规格：34px 高、`radius-md`、`bg-layer-3`、0.5px `border-l4`、聚焦 `state-business-primary` |
| 状态条 | 左侧 2px 状态色实边 + 同色 10% 底的提示条；历史回填进度条在其中显示百分比；失败/成功/进行中三态 |
| 分组标题 | 「日常画像」「技术画像」两级标题 + 每组生效条数徽标，粘性吸顶 |

图标是把官方 `@deepseek-ai/dsh-client-ui-primitives` 的 `*Regular` 路径数据**内联**进面板的（10 个字形，逐字节由 `portrait-icons-check.mjs` 与官方源码比对），**不是** require 那个包 —— 原因见第 6 节约束 ④。样式表由插件自己 `document.head.appendChild(<style data-plugin data-plugin-css>)` 注入（模块表里**没有** `styles` 这个模块字），插件卸载时随之移除。34 个 `--dsw-*` 主题令牌全部经过与主题包导出清单的比对，`portrait-css-check.mjs` 另外禁止出现任何硬编码颜色。

### 本地设计预览（离线、单文件）

面板的设计被固化成一份**自包含**的本地文件，不需要网络、不需要启动应用：

```

```

## 2. 工作原理

```
你发消息
   │
   ├─ agent/inbox/inserted ─────────────► 记录「真人输入」时间戳（用于排除插件注入的上下文）
   │
你这一轮结束
   │
   └─ session/event(turn/end)
         │  折叠本轮事件：turn/start → turn/end 之间的 user/message + assistant/message + tool/call
         │  只保留 source.kind === 'user' 的真人发言（插件注入的 user 角色消息会被排除）
         ▼
   后台作业队列（一次只跑一个，不阻塞对话）
         ├─ 轮次摘要：ctx.llm.stream() ──► turns/<session>.jsonl（+ 证据入 evidence.jsonl）
         │        来源已就绪时，默认每轮触发一次画像合并（synthesizeEveryTurns=1）
         ├─ 画像合并：现有画像 + 新证据 ──► profile.json / profile.md
         └─ 会话概要：agent/disposed 时用模型重写 sessions/<session>.json 的 rollup
                         （在此之前先是本地确定性推导版，保证面板永远有内容）

新会话开始
   └─ systemPrompt.section（仅该会话开启画像开关时）：同步读取内存缓存，注入一小段提示
         └─ 模型按需调用 portrait_read / portrait_search / portrait_history / portrait_maintain
```

要点：

- **提炼调用走 `ctx.llm.stream()` 直连模型**，不开子代理会话 —— 不需要 parent agent、不在 UI 里留下子会话、不被进行中的对话干扰。
- **敏感信息在写入前脱敏**：`sk-` / `ghp_` / `AKIA` / JWT / 私钥 / `password=` 等会被替换为 `[已脱敏]`，脱敏发生在写盘与送模型之前。
- **失败被隔离**：单个后台作业失败只记日志，不影响对话；单个工具注册失败只损失该工具。

## 3. 数据存放位置

默认写到 `<DSH_HOME>/user-portrait`（未设置 `DSH_HOME` 时为 `~/.dsh/user-portrait`），可用 `dataDir` 覆盖：

```
<DSH_HOME>/user-portrait/
├── profile.json         画像主文档（9 个维度 + 备注），程序读取用
├── profile.md           同一份画像的 Markdown 版，供人阅读/手改参考
├── evidence.jsonl       追加式证据账本（每行一条 JSON），含原文片段与来源
├── state.json           逐会话轮次水位、已处理会话、提炼节流计数、会话开关
├── blacklist.json       证据黑名单（行键 / 轮次键，两层）
├── deleted.log          物理删除审计（只追加，不读回）
├── client-report.json   面板自证回传（排查空白面板用）
├── sessions/<id>.json   单个会话的整体概要 + 逐轮摘要
├── turns/<id>.jsonl     单个会话的逐轮摘要（追加式）
└── views/<id>.md        单个会话的可读 Markdown 记录
```

### 记录格式示例

单轮摘要（`turns/*.jsonl` 一行）：

```json
{
  "turn": 8, "at": 1760000000000, "outcome": "已完成",
  "userAsk": "把插件挪到 work-space，并把 dataDir 改成绝对路径",
  "userKeyPoints": ["用 PowerShell 而非 node", "dataDir 要绝对路径"],
  "assistantSummary": "搬移目录并固定绝对数据目录。",
  "corrections": [{ "kind": "偏好", "text": "倾向用 PowerShell 而不是 node 做文件操作" }],
  "evidence": [
    { "dimension": "skill", "text": "优先使用 PowerShell 处理文件操作",
      "confidence": "high", "source": "最好用 PowerShell 而不是 node" }
  ]
}
```

画像条目（`profile.json` 中 `dimensions.<id>[]` 的一项）：

```json
{
  "text": "优先使用 PowerShell 处理文件操作",
  "confidence": "high",            // high | medium | low
  "status": "active",              // active | superseded | retired
  "sources": [{ "sessionId": "session-…", "turn": 8 }],
  "firstSeenAt": 1760000000000, "lastConfirmedAt": 1760000000000,
  "manual": true                   // 存在时表示由你手动写入/纠正过
}
```

> 这些文件都是**纯文本**，可以随意 git 备份、手改、diff。手改后 `profile.json` 会在下次读取时被规范化（未知字段保留、缺失维度补齐、旧维度折叠到合并后的维度）。`version: 3` 表示带 `statement` 依据标记的 9 维度 / 2 分组结构。

## 4. 配置项

配置写在 bundle 补丁里：[cordis.patch.yml](./cordis.patch.yml)。改完需要重启 DSH Desktop 生效。

| 键 | 默认 | 说明 |
|---|---|---|
| `dataDir` | 空（→ `DSH_HOME/user-portrait`） | 画像数据目录；留空即默认位置，填相对/绝对路径则按该位置 |
| `enabled` | `true` | 总开关 |
| `loadHint` | `true` | 是否允许注入「画像可用」系统提示段；每个会话还要在输入框旁打开画像开关 |
| `backfillOnStart` | `true` | 随包补丁设为 `false`：不在启动时回填历史，画像从新会话开始积累 |
| `synthesizeEveryTurns` | `1` | 每积累多少轮重新合并一次画像维度（`0` = 不自动合并） |
| `turnSynthesisDelayMs` | `3000` | 每轮提炼的合并窗口（毫秒）；`0` = 立即执行 |
| `minEvidenceForSynthesis` | `3` | 少于这么多条新证据就跳过合并 |
| `rollupOnDispose` | `true` | 会话结束时是否用模型重写会话概要 |
| `sessionRollupMinTurns` | `3` | 少于这么多轮的会话不写模型概要（下限 1） |
| `provider` / `model` | 空 | 后台提炼的模型路由；**都留空则自动沿用你当前的默认模型**（`.dsh` 的 `agent-default-model`）。要固定就两个一起填 |
| `limits.perUserMessage` | `6000` | 单条用户消息送入提炼前的字符上限 |
| `limits.perAssistantTurn` | `4000` | 单轮回答送入提炼前的字符上限 |
| `limits.synthesisEvidence` | `80` | 单次画像合并最多喂入多少条证据 |
| `limits.maxOutputTokens` | `4000` | 提炼调用的输出上限；触顶即丢弃该次结果（不写半截 JSON） |

## 5. 怎么用

### 看画像 / 纠正

- **右栏 →「人物画像」标签页**；也可点会话头部的「画像」按钮，或走 设置 →「人物画像」。
- 四个页签，顺序固定为：**画像维度** · **我的备注** · **会话记录** · **证据时间线**。
- 「画像维度」页顺序：**置顶的检索条**（输入即筛，见 §⑫）→ 新增/上限/导出 → **日常画像 / 技术画像** 两组 → **废弃区（最底部，见 §⑪）**。
  **我的备注只在它自己的页签里**，不在维度页重复一份（此前两处都渲染同一列表，容易误以为存在两份备注）。
- 每条条目可：改文字、升降置信度、废弃/恢复、删除。备注与手动纠正**不会被后续自动提炼覆盖**。
- 顶部按钮：立即重新提炼（主操作） · 回填全部历史会话 · 重新提炼全部历史 · 刷新 · 反馈与建议；后两者为 `outline` 变体，悬停显示时间戳、数据目录与未配置项。

### 让模型用画像（四个工具）

| 工具 | 作用 |
|---|---|
| `portrait_read` | 读取画像（可按 `dimension` 过滤、可 `includeRetired` 看历史条目） |
| `portrait_history` | 读取会话记录与逐轮「我问/你答」要点（可按 `sessionId` 定位） |
| `portrait_search` | 在证据与逐轮记录中按关键词检索，核实某条结论的原文依据 |
| `portrait_maintain` | 手动纠正、增删备注、`backfill` / `redigest` / `synthesizeNow` |

### 想回填历史会话

三选一：
1. 面板点「回填全部历史会话」；
2. 让模型调用 `portrait_maintain(action: "backfill")`；
3. 把 `backfillOnStart` 改成 `true` 并重启。

回填按会话逐个提炼、每完成一个落盘一次，随时可停。

## 6. 四条必须遵守的运行时约束（都踩过坑）

维护这个插件时，以下四点**不是风格偏好，而是硬约束**。它们分别导致过「每一轮对话直接失败」「四个工具全部消失」和「面板一片空白且日志里什么都没有」。

### ① `systemPrompt.section` 的 `text` 必须**同步**返回字符串

`dsh-system-prompt` 第 342 行是同步求值：

```js
text: typeof section.text === "function" ? section.text(context) : section.text
```

紧接着 `interpolate()` 会执行 `text.indexOf("{{")`。如果 `text` 写成 `async` 函数，框架拿到的是 **Promise** → `text.indexOf is not a function` → **整轮对话在 step 1 失败**。

做法：`store.cachedProfile()` 暴露内存缓存，提示段用纯同步函数读取；异步加载只发生在后台作业里。

### ② `ctx.tools.register()` 只接受**严格 JSON Schema**

`register()` 用 `assertSupportedJsonSchema(output.schema)` 校验，允许的关键字仅：
`type` / `properties` / `required`（**对象级的字符串数组**）/ `additionalProperties` / `items` / `enum` / `const` / `oneOf` + 注解 `description` / `title`。

**属性里写 `required: true` 是非法的**（那是 `defineTool()` 辅助函数的简写输入格式）。本插件是工作区外链包，**import 不到 `@deepseek-ai/dsh-tools`**，所以 schema 一律手写成严格形式，并在测试里用**运行时自己的校验器**验证。

另外：`parameters` 不会被 `register()` 校验，会被**原样**交给模型 —— 写错不会报错，只会让模型看到错误的参数表。

### ③ 注册必须用 `ctx.inject([...])` 等服务就绪

本插件**不声明任何依赖**，因此激活得极早 —— 早于 `tools` / `webServer` / `llm` / `sessionQuery` 被提供。若在 `apply()` 里用：

```js
const tools = ctx.get('tools');
if (tools !== undefined) { /* … */ }   // ← 服务还没提供，静默跳过
```

注册会被**静默跳过**：面板路由 404、工具一个都不注册。正确做法：

```js
ctx.inject(['tools'], (toolCtx) => { toolCtx.tools.register(definition); });
ctx.inject(['webServer'], (webCtx) => { webCtx.webServer.register(route); });
ctx.inject(['systemPrompt'], (promptCtx) => { promptCtx.systemPrompt.section({ … }); });
```

`ctx.inject` 会启动一个**带依赖的子插件**，服务出现才执行回调；各关注点独立门控、互不牵连。`llm` / `sessionQuery` 是调用时才读取，不受此影响。

### ④ 客户端半边只能 require 平台种子字，样式表必须自己注入

客户端半边跑在**模块表**上（`window.__ModuleLoader__`），`require` 只认平台种子字：
`react` / `react/jsx-runtime` / `react-dom` / `react-dom/client` / `@deepseek-ai/cordis` / `@deepseek-ai/dsh-client-store` / `@deepseek-ai/dsh-client-ui-slots` / `@deepseek-ai/dsh-client-ui-primitives` / `@deepseek-ai/dsh-client-ui-dockkit`。

两条踩过的坑，症状**完全一样**：面板一片空白，Host 日志里只有正常的 `ready` 与路由注册，没有任何报错。

1. **`require('styles')` 不存在。** 模块表里没有 `styles` 这个字：客户端包各自把 CSS 塞进 `<style data-plugin data-plugin-css>`（`dsh-client-modules` 卸载时按 `data-plugin` 收集）。旧代码用 `require('styles')` + try/catch 静默失败，于是**面板从来没有被上过样式**，`.dup-root` 的 `height:100%` 直接塌成 0 —— 看着就是空白。现在 `installStylesheet()` 自己注入，卸载时移除。
2. **不要 require `@deepseek-ai/dsh-client-ui-primitives`。** 它虽然在种子表里，但**安装版的顶层 import 是 `react-dom` / `katex` / `shiki/core`**，这些都不是种子字，`require` 会在工厂求值阶段抛错；slot 服务对抛错的条目是**隔离丢弃**（`reportEntryError`），于是整个面板消失。需要官方图标就把路径数据内联（本插件已内联 10 个，`portrait-icons-check.mjs` 逐字节比对官方源码）。

审计由 `portrait-css-check.mjs` 守着：它会枚举 `client.js` 里所有 `require(...)`，任何一个不在种子表里就失败；`portrait-client-check.mjs` 的模块表桩也**只提供 `react`**，让同样的错误在测试里立刻炸出来。

### ⑤ 空白面板的七条成因与现在的防线

真实故障现象：右栏页签**有标题**、点进去**内容全空**，Host 日志只有正常的 `ready` 与路由注册，`test/` 测试全绿。已确认的成因与对应防线：

| 成因 | 为什么会空白 | 现在的防线 |
|---|---|---|
| `require('styles')` 不存在（约束 ④-1） | CSS 从未注入，`.dup-root` 高度塌成 0 | 自己注入样式表；`portrait-css-check.mjs` 审计 require |
| 模块表里 require 了非种子字（约束 ④-2） | 工厂求值抛错，slot 条目被隔离丢弃 | 图标改为内联；同上的 require 审计 |
| `apply()` 中途抛错（席位名/重复 key/注册表缺失） | 页签类型已注册（标题有了），但**内容体没注册** | 每个席位各自 `try/catch` 独立注册，失败收集进 `failures` 并通过 `onSeatFailures` 显示在面板顶部 |
| 内容体的 `key` 写成了 tab 的 kind | 宿主按 `entryKey: definition?.id ?? tab.kind` 派发内容体，即按 `definition.id` 查；用 kind 当 key **永远查不到**，面板只剩「不可用」兜底 | 内容体的 `key` 必须是**页签类型的 id**（= 插件包名），`portrait-client-check.mjs` 断言 `key === tabDefinition.id && !== tabDefinition.kind` |
| **`sidebarRightTabs` 还没被 provide** | 插件不声明依赖 → 激活极早 → `ctx.get('sidebarRightTabs')` 拿到 `undefined` → **页签类型从未注册**。宿主对未知类型给兜底，于是有页签、内容空 | 不"取不到就算了"：`registerTabType()` **有界重试**（40 × 500ms）等服务出现，成功即停；结果回传 Host（`tab-type-late`）。定时器由 `ctx.effect` 持有，插件卸载即停。客户端测试故意让服务缺席，再交付服务并驱动重试，断言"类型注册成功、重试停止、结果已回传" |
| **同一类型被注册两次**（两种触发） | ① 重载后**上一次的注册项仍留在注册表里**（它的 disposer 挂在已死掉的 fiber 上，从没被调用），新一次注册必然抛 `tab type id "…" is already registered`；② `apply()` 被再次执行。两者都让面板顶部常驻一条"1 处入口注册失败"警告 | **①「已存在」视为成功**：`isAlreadyRegistered(error)` 匹配到就返回 `{state:'registered'}` —— 期望的终态（类型存在）已经成立，不该报错；**②幂等闩按注册表实例记**，同一实例再调用直接视为已完成，**不同实例**（新上下文）仍会正常注册，真实失败不会被吞掉；**③注册返回的 disposer 交给 `ctx.effect`**，重载时真正注销，下一次不再撞车。客户端测试先在一个"注册表总是抛已注册"的上下文里断言 `failures` 为空（把守卫去掉会实测失败），再连跑两次 `apply()` 断言只注册一次、第二次无失败 |
| **钩子写在提前 return 之下** | 加载态/错误态那次渲染不调用该钩子，数据到达后调用 → 钩子数量变化 → React 抛 **#310** → 整棵树崩掉（错误边界出现前就是一片空白） | 所有 `useState`/`useRef`/`useEffect`/`useCallback` 必须在任何 `return` 之前。`portrait-client-check.mjs` 逐次渲染记录**钩子顺序**并断言每次都一致（把钩子放回错误位置实测会报 `[16,17,17]`） |

排查这类问题不要再靠推断：**插件会自己上报**。浏览器半边把 `tab-type` / `tab-type-late` / `seat-declared` / `body-registered` / `mounted` / `snapshot` 六个阶段回传到 Host，落在 `<dataDir>/client-report.json`（也可 `GET /api/user-portrait?view=report`）。上面第 5 条就是这个机制在一次真实故障里直接指认出来的（`tabsService: unavailable` 却 `body-registered: ok`）。

此外面板整体包在 `PortraitBoundary`（React 错误边界）里：任何渲染期异常不再表现为空白，而是显示「面板渲染失败：<错误信息>」+「重新挂载」按钮 —— 第 6 条就是靠它从"空白"变成 `Minified React error #310` 才定位到的。`portrait-boot-check.mjs` 会用 app 自己的 React 18.3.1 真实执行工厂、`apply()` 与整棵组件树，把这一类失败在测试阶段就抓出来。

### 附：路由不会被桌面版截走

`dsh-host-webserver` 的匹配规则是 **exact 未命中后「Longest-prefix-wins」**，所以 `/api/user-portrait` 会赢过桌面 RPC 自己的 `/api`。

### ⑥ 三条运行期的硬约束（合成、重载、后台作业）

| 约束 | 踩过的坑 | 现在怎么做 |
|---|---|---|
| **合成必须按维度分次调用** | 原来一次要模型"输出合并后的完整画像"（全部 9 个维度 × 现有条目 × sources/note/status）。画像一有内容，回复就超过 `limits.maxOutputTokens`，而被截断的回复是**整批丢弃**的 —— 于是 `profile.json` 从未生成，证据账本里明明躺着 galgame/病娇 也进不了画像（提示词里那句 60 字上限与实际输出量的矛盾就是这么暴露的） | `SYNTHESIS_SCOPES`：日常组一次、技术组**每个维度一次**（每次提示词约 1.7k 字符）。`mergeSynthesis` 变成**增量**：回复里没有的维度**原样保留**（不会被误标 `superseded`），只有回复里出现的维度才做合并。一个维度失败只损失该维度 |
| **后台作业不能因插件重载被掐死** | `ctx.effect(() => () => bg.abort(new Error('user-portrait disposed')))` —— Host 一改插件文件就自动重载，于是你点"回填全部历史会话"后立刻看到 `user-portrait disposed` | 后台服务解析改走 **root 上下文**（`ctx.root.get(name)`），它比任何实例都长寿；**不再在卸载时 abort**；`PortraitEngine` 拿到 `isCurrent()` 代际门：被新实例取代就停手，且**只有活着的实例才合成**（避免旧实例把过期画像盖回去） |
| **一次点击应当只做一个动作** | "重新提炼全部历史"= redigest（重下所有会话），语义和"回填未处理"重复且更贵 | 两个按钮各自明确：`backfill` 只处理未处理过的会话，`redigest` 强制重做全部（`force: true`） |

> 画像为空时不必等自动节流：点一次「立即重新提炼」即可，它会把账本里的证据按维度合并进 `profile.json`，并在写入前**再合并一次同类结论**（所以条数通常比证据条数少）。`test/portrait-synthesis-verify.mjs` 就是拿**真实账本**跑这条路径，断言 galgame 那两条证据最终落成**一条**画像结论。

### ⑦ 提炼范围与置信度模型（谁说的话才算证据）

画像的核心约定：**结论的依据只有三种可能** —— 用户的原话（`user`）、模型自己的应答（`assistant`），或两者合并后的（`mixed`）。每条条目都带一个 `statement` 字段：

| `statement` | 含义 | 面板文案 | 初始置信度 | 上限 |
|---|---|---|---|---|
| `user` | 依据能追到**用户原句**（含纠正、偏好、红线） | 依据 · 用户的话 | `medium` | `high` |
| `assistant` | 依据出自**模型的回答 / 解释 / 方案** | 依据 · 模型应答 | `low` | **日常画像 `medium`；技术画像 `low`** |
| `mixed` | **一条结论同时建立在两种依据上**（合并产物） | 依据 · 用户的话 & 模型应答 | 按含推断处理 | **同 `assistant`（日常 `medium` / 技术 `low`）** |

- **`mixed` 由合并产生，不是模型声称的**：把一条 `user` 与一条 `assistant` 并成一条时，`statement` 记为 `mixed` —— 记成 `user` 会把"其中一部分是推断"这件事抹掉。同为依据合并则保持原值（`user`+`user` 仍是 `user`）。
- **`mixed` 的置信度按"含推断"计算**：它不能借用用户那一侧挣来的高置信度。技术类里 `mixed` 一律停在 `low`，日常类最高 `medium` —— 与"只看用户的话判断会不会某项技术"是同一条原则。
- **`user` 必须有原句可查，不能只是声称。** 逐轮提炼时，模型为 `user` 条目提供的 `source` 必须与用户本轮发言逐字对得上（允许≥80% 字符二元组覆盖的轻度改写）；对不上、或根本没给引文，就**降级为 `assistant` 并压低置信度**。合成阶段再核一次：`user` / `mixed` 条目至少要有一个 `sources` 指向**已验证为用户原话**的证据行，否则同样降级。
- **纠正类靠"锚定"而不是逐字引用**：纠正文本是模型对用户抱怨的概括，不可能逐字命中；因此改为在用户本轮发言里找**共享 ≥4 字符**的最接近一行，找到就以该行为 `source` 并保留 `user`，找不到则视为模型杜撰、降为 `assistant`。
- **技术画像（skill / workstyle / boundary / friction）严格看用户的话。** 看过解释、采纳过方案、提到过某个技术，都**不等于**用户了解或掌握它；这类 `assistant` / `mixed` 条目一律停在 `low`，只有用户自己的话（或手动改）才能提升。
- **日常画像**里模型的应答可以作参考补充（上限 `medium`）；与新证据指向同一件事时**合并成一条**，两种依据都用上时记 `mixed`，置信度取较高值后按上限夹紧。
- **`statement` 缺失即视为 `assistant`（严格模式）**：想标 `user` 必须明确写出并被原句验证 —— "沉默"不能变成"用户说过"。
- **提炼必须主动产出两类证据**：`user`（用户明确说过的，附逐字原话）+ `assistant`（只有从应答侧才看出的线索，如追问方向、采纳/拒绝方案）。只产 `user` 会让 `mixed` 永远无法出现。
- **升降与删除**：用户再次提到 / 确认 / 展开 → 升一级；否定或回避 → 降一级；多次反向或明确说“不是这样” → 标为 `retired`（**保留在历史里、可恢复**，不物理删除）。
- `manual: true`（手动新增或手动改过）的条目**不受策略约束**：置信度由用户自己定，模型不得覆盖。
- **手动调整不受依据限制（本轮修正）**：点「升为高 / 降为低」把一条 `assistant` / `mixed` 结论改成 `high` 后，**它就保持 `high`**。此前 `normalizeProfile()` 每次加载都会重新夹紧，连 `manual` 条目一起夹，导致手动升到高处一刷新就被打回（技术类回 `low`、日常类回 `medium`）。现在 `clampConfidence(confidence, statement, group, manual)` 在 `manual === true` 时直接返回用户选的值；依据上限只管模型能声称的置信度。面板上这类条目的悬停改为"手动设置，不受依据上限限制"。
- 策略由**代码强制**，不只写在提示词里：`lib/schema.js` 的 `confidenceCeiling()` / `clampConfidence()` 定义上限，`lib/extract.js` 的 `isTraceableToUser()` / `statementForCandidate()` 负责核验，归一化与合并时都会夹紧（`manual` 除外）。`PROFILE_VERSION` 为 **3**，旧文档条目默认视为用户的话并重新夹紧（一条旧的 `assistant` 条目若写着 `high`，加载时回到 `low`；手动条目保持用户设定）。

#### 旧数据的一次性回填（为什么曾出现"整份画像全是用户的话"）

`statement` 字段是后加的，这之前的账本行没有它。而核验逻辑当时把"没有标记"当作"用户的话"放行，于是：

- 本机实测 **114 行账本里 90 行无标记**，画像 **119 处出处里 93 处指向这些行** → 整份画像读作 `user`；
- 同时账本里 **`assistant` 行数为 0**（提炼只产 `user`）→ `mixed` 不可能出现。

现在由 `lib/migrate.js` 在启动时**自动回填一次**（`EVIDENCE_BASIS_VERSION = 2`，记录在 `state.json`）：

1. 逐行拿它的 `source` 去**真实会话原文**里查（`sessionQuery.readSession` → `foldTurns`）：对得上 → `user`；对不上或无引文 → `assistant`。
2. 纠正类按"锚定"重判（与用户某一行的共享连续字符 ≥4）。
3. 按重写后的账本**重算画像条目的依据**：来源里出现 `user` → `user`；两种都有 → `mixed`；只有推断 → `assistant`，并重新夹紧置信度（手动条目不动）。
4. 改写账本前把原文件复制为 `evidence.jsonl.before-basis-migration`；迁移只跑一次，之后的启动直接跳过。

**两条防护**（都踩过）：

- **读不到原文的行不猜**：会话读不出来时，该行**保持无标记**而不是被猜成 `assistant`；无标记的行**不能**再为任何结论背书（`statementForCandidate` 只认 `statement === 'user'` 的行）。这样"暂时读不到"不会把历史改坏，只是这几条结论暂时拿不到用户依据。
- **一条原文都读不到就整体跳过**：若 `readableTurns === 0`（会话服务没就绪、存储被移动），迁移**不写任何东西**、不记版本号，下次启动重试 —— 否则一次临时故障会把整份账本刷成"模型应答"。

条目出处只记到"会话#轮次"，一轮可能有多条依据，因此重算时会**按条目文本优先匹配具体那一行**（匹配不到才用该轮的全部依据）。

### ⑧ 来源展示：默认只给计数，悬停才给出处

条目不再把会话与原文印在正文里：

- **默认**：`来源 3 处`（虚线小字，可聚焦）。
- **悬停**：展开 `会话 · 第 N 轮 · 时间` 与**原文摘录** —— 要核实原文时一次悬停就能看到，平时不占版面。
- 每条还带依据标签：`依据 · 用户的话` / `依据 · 模型应答` / **`依据 · 用户的话 & 模型应答`**（第三种是两种依据合并后的结论，有独立配色与说明，提示其中含推断）。
- 时间线同样处理：行内只留 `会话#T轮次 · 时间`，原文进悬停卡片。
- 助手读画像（`portrait_read`）看到的是 `[置信度/状态/依据·来源N处]` 加一行 `出处: 会话#T轮次`：结论与出处可核对，原文摘录仍留在 `evidence.jsonl` 里、不随画像外泄。

出处里的**时间与原文由 Host 从证据账本回填**（`sourceIndexOf()`），不要求模型在回复里重写一遍 —— 既让悬停卡片完整，又不让合成回复重新膨胀到超出输出预算。

### ⑨ 合并优先：同类结论并成一条，尽量不新开条目

**踩过的情况**：同一件事被拆成两条 ——
`喜欢玩 galgame（日式视觉小说），尤其对病娇女主/病娇题材有兴趣` 与
`挑选 galgame 时看重剧情质量和制作水准，不只看题材是否对口`。
两条都属于"关于 galgame 的偏好"，却各占一行，画像因此越堆越碎。

**现在的规则：先比对，再新建。**

- 新建条目前，先在**同一维度已有条目**里找是否说的是同一件事；是就**合并**（内容并进 `text`、`sources` 合并、置信度取较高；`statement` 同依据取原值，两种依据并用则记 `mixed`）。
- 只有**新主题**，或与已有结论**明显冲突/出入较大**时，才新开一行。
- 同一主题的"不同侧面"（同一个人 / 游戏 / 技术 / 习惯）属于同一条结论，不拆分。
- 一个维度尽量保持 **3-5 条** `active`；超标时优先合并最相近的两条，而不是继续增加条数。
- 判定"同一件事"的规则（`lib/extract.js` 的 `isSameConclusion()`），共 **5 条触发条件**：
  1. 两条文本相同、或一条包含另一条（"主要用 Windows" ⊂ "主要用 Windows 处理日常任务"）；
  2. 字符二元组 Dice 相似度 ≥ 0.55（换个说法、语序调整）；
  3. **共享同一个专有名词**（`galgame`/`PowerShell`/`VNDB`…，允许 `galgame` vs `galgames` 这种词形差异）；中文泛指词不算专有名词，所以两条无关的中文结论**不会**被误并；
  4. **同一对象的多个要求 → 合并**：两条都是"要求/偏好"语气（`要求|必须|不要|应该|优先|避免|禁止|偏好|倾向…`），且把这类语气词剥掉后仍共享 **≥3 个连续字符**。例：`要求把 VNDB 标签分开分级` + `要求把 2DFan 标签分开分级` → 一条；而 `不要用 iframe 方案` + `不要用 node 做文件操作` 因剥掉"不要用"后无公共段而**保持两条**；
  5. **同一流程的多个步骤 → 合并**：两条都含流程词（`先|首先|然后|接着|之后|最后|再|步骤|流程|顺序…`）且剥掉流程词后共享 **≥3 个连续字符**。例：`先备份再改文件` + `先备份再改，然后验证` → 一条流程结论。
- 合并的两道闸门是叠加的：提示词要求模型主动合并，`mergeSynthesis()` 在写入前**再做一次**合并，模型没合并的也会被兜住。
- 每次合成会记录合并数量：`synthesis applied (…): N entries accepted, M folded into existing conclusions, K preserved`。
- **回归保护**：`portrait-smoke.mjs` 覆盖"同一回复内同主题拆成两条 → 合成一条且两条信息都在""改写已有结论 → 并入而不新增""不同主题不被误并""合并取较高置信度""同对象要求合并 / 无关要求不并""同流程步骤合并 / 不同流程不并"；`portrait-synthesis-verify.mjs` 用**真实账本**断言 galgame 那几条最终落成 **1 条**。这里还抓出过一个真实缺陷：被并入的**已有条目**若没有同时并入结果集，整条会从画像里**消失**（已修，并有断言守着）。

### ⑩ 置信度可升可降 + 低置信度用红色

- 每条条目有**两个独立按钮**：`升为高/升为中` 与 `降为中/降为低`（已在端点时显示 `已最高` / `已最低` 并禁用）。
  早先只有一个"升/降"切换按钮，只能往上走 —— 一条被误升的结论在面板里**无法降级**，这是缺陷不是设计。
- 置信度用官方 Tag 几何、只有色板不同：`高` = success（绿）、`中` = warning（琥珀）、**`低` = 红色**。
  低置信度用的是**与"高"完全相同的组件与几何**（同一 `Chip`、同样 10% 染色底 + 同色文字），只把颜色换成 `--dsw-alias-state-error-primary` —— 所以"低"和"高"看起来是同一级别的东西，只是警示色不同，不再是一条灰字。
- 这两个按钮**常驻可见**（不藏在悬停里）：升降置信度是高频操作，不该靠发现。
- 手动改过置信度的条目会带上 `manual: true`：这是**你自己的判断**，此后不再受 `statement` 上限约束（模型也不能覆盖）。
- 时间线里的置信度标签同样按这套色板渲染。

### ⑪ 废弃区：安放已废弃 / 已取代 / 已删除的结论

面板「画像维度」页的最前面有一个与维度同级的「废弃」区（`data-section="discard"`），框架与画像维度完全一致（同一套 `dup-section` 卡片 + 维度分组标题）：

- **安放三种结论**：`retired`（已废弃）、`superseded`（已取代）、被**删除**的条目。
- **维度卡片只显示 `active` 结论** —— 一个维度读起来就是"当前相信什么"；历史不再混在生效条目里（此前靠一行"· N 条历史"暗示，容易误读）。
- 区块默认**收起**（只显示"废弃 · N 条"与一行说明），点「展开」列出各维度的废弃条目；每条都能点「恢复」回到原维度。
- 复用 `setStatus active` 恢复时会**清掉 `deletedAt`**，所以恢复后的条目是一条正常的结论，而不是半废弃状态。

**两级删除**（软 / 硬各一层，意图不会混淆）：

| 位置 | 按钮 | 行为 | 可逆 |
|---|---|---|---|
| 维度卡片 | 删除 | `removeEntry` → 标 `retired` + `deletedAt`，移入废弃区 | **可恢复** |
| 废弃区 | 删除 | `purgeEntry` → **物理删除**该条目 | **不可逆**（需二次确认） |

- 废弃区的删除是**两步**：第一下只武装，按钮变成「确认删除？」，5 秒内再点才真正删除；不点则自动取消。判定用的是 ref 而不是闭包状态 —— 依赖旧闭包会导致"点了没删"，而悄悄失效的删除比不删更糟。
- **证据时间线同步**：删除条目时，会一并移除**只属于它**的证据行。判据有两条，缺一不可：
  1. 该行所在轮次**没有别的结论**引用（同一轮的共享证据保留，否则会把别人的依据一起弄没）；
  2. 该行确实支撑这条结论（文本/引文对得上，避免误删同轮里无关的证据）。
  被保留下来的共享证据会在返回里报数，面板提示 `（N 处证据仍被其它结论引用，已保留）`。
- **删除审计**：每次物理删除追加一行到 `<dataDir>/deleted.log`（时间、维度、文本、依据、置信度、来源、删掉几条证据、保留几处共享）。它不是备份、不会被读回画像，只用于事后解释"那条结论怎么没了"。
- 时间线本身不需要另行清理：账本行被物理删除后，快照里的证据列表自然不再包含它们。

### ⑫ 置顶检索：输入即筛，只搜画像结论

**踩过的坑**：检索曾是独立页签，点「检索」会 POST 到 Host，然后**把返回结果丢掉** —— `renderSearch` 只渲染输入框和按钮，`run()` 既没把结果存进 state 也没渲染，所以点了完全没有反应（测试也只断言了"有输入框"，没断言结果）。

**现在**：

- 检索条**置顶在「画像维度」页**，删掉了独立页签（页签回到 4 个）。它不是一次网络请求，而是**内存内的即时过滤**：`profile` 本来就在面板里，每个按键都会重算命中，无需等待、也没有"请求失败"这种失败模式。
- **只搜画像结论**（维度名 + 结论文本 + 备注），不搜证据账本与逐轮记录 —— 面板要回答的是"画像里关于 X 相信什么"，把原始记录混进来只会让结果不可读。
- 命中条目带上下文：**维度 · 置信度 · 依据（用户的话/模型应答）· 来源 N 处**，非 `active` 的还带状态标签；命中词用品牌色 `color-mix` 高亮（`<mark class="dup-mark">`，不写死颜色，跟随主题）。
- 空结果会明说「没有命中的结论」并给「清空」入口；点击命中项可**定位**到下方对应条目（`data-entry-id` + `scrollIntoView`，若目标在废弃区会先展开它）。
- 检索区不改变下方画像列表 —— 它是一层"查找"，不是过滤器，画像始终完整可读。

### ⑬ 条目寻址：id 必须与数组位置无关

**踩过的坑**：条目 id 曾是 `${维度}:${数组下标}:${firstSeenAt}`，而面板用的是**上一次渲染时的下标**。后台每几轮就自动合成一次，合并/新增条目会让下标整体错位，于是点"废弃"时报
`没有找到 id 为 friction:8:1792162973811 的条目`。

**现在**：

- id 由**条目文本**派生（`entryId()`：`维度:FNV-1a 指纹`），与位置、时间戳都无关。
- `normalizeProfile` 在加载时把磁盘上遗留的位置型 id **重写成稳定 id**，所以"存什么"与"面板收到什么"永远一致。
- 查找还会做两层兜底（`findEntryIndex()`）：先比现算的稳定 id，再比客户端一并送来的**条目原文**（`matchText`）。因此"快照渲染 → 后台合并 → 你再点击"这种时序也点得中；真正不存在的 id 仍然**明确报错**，不会静默改错行。
- 客户端每次条目操作（编辑 / 升降置信度 / 废弃 / 恢复 / 删除）都附带 `matchText`，这也是 `friction:8:…` 这类历史 id 仍可恢复的原因。

### ⑭ 提炼时机与实时更新（每轮一答后就地更新，且安静）

**提炼时机**：每轮 `turn/end` 先做**摘要**（1 次调用），然后：

- **没有新证据 → 一次模型调用都不发**（日志记 `synthesis skipped (turn): no fresh evidence`）。
- **有新证据 → 只合被它触达的维度**：日常维度合并成 1 次调用，每个技术维度各 1 次。典型一轮只碰 1-2 个维度，所以是 1-2 次小调用，而不是过去那种固定 5 次的整份重写。
- **3 秒合并窗口**（`config.turnSynthesisDelayMs`，默认 3000，设 0 立即执行）：连续追问时把维度并入同一批，窗口关闭后跑一次，避免一轮一调用排队。
- **边界**：只在正式会话（`origin !== 'subagent'`）、只在 `turn/end`、且该轮可提炼时触发。
- 节奏由 `config.synthesizeEveryTurns` 控制，**默认已改为 1**（每轮）；调大即回到"每 N 轮批一次"。

**面板更新**：删掉了每 20 秒轮询整份快照的做法。

- Host 侧 `GET /api/user-portrait?view=stream` 是 **SSE**：连接建立时发一次 `hello`（带 `updatedAt` 与条目数），此后**每次画像写入才推一个 `profile` 事件**；空闲时只有一条 30 秒的无数据保活注释。
- 面板用 `EventSource` 订阅：收到更新的 `updatedAt` 才重新取快照；版本号单调递增（取最大值）并去重，所以同一版本不会触发第二次拉取。
- **没有流就完全不刷新**：`EventSource` 不可用时面板保持静默，只有手动刷新会更新（不会退化成轮询）。
- 刷新按钮：重读磁盘并**明确回报**「已刷新 时间 · N 条生效 · 画像更新于 … ·（条目 +2 / 内容无变化）」，刷新中按钮显示「刷新中…」。此前它静默重读，数据没变时看起来像坏了。
- **回填结果只显示 8 秒**（`BACKFILL_BANNER_MS`）：此前只要 `total > 0` 就渲染"已完成 17/17"，于是永远不消失。
- **运行中的进度会被跟踪**：`load()` 在 `backfill.active === true` 时每 2 秒重读一次，运行结束后不再排下一次读取——否则面板会停在第一次拿到的数字上，因为 Host 只在画像写入时推送，逐会话的进度变化不会触发推送。
- **计时从完成时刻算起**：窗口从 `finishedAt` 起算，不从点击时刻算；运行中永远显示"进行中 x/y"，完成后才换成"已完成 x/y"并开始 8 秒倒计时。
- **卡死的运行会自愈**：`active` 超过 30 分钟视为失效（`BACKFILL_STALE_MS`），再次点击会重新开始，避免按钮被一次挂起的模型调用永久锁住。

### ⑮ 导出、结论上限、证据黑名单与反馈入口

**按钮顺序**（「画像维度」页、手动新增条目之后）：`手动新增条目` → `结论上限` → `导出`。工具栏里 `刷新` 之后是 `反馈与建议`。

**版面**：本页顺序是 `检索` → 新增/上限/导出 → 日常画像 → 技术画像 → **废弃（最底部）**。废弃区是"存放处"而不是主体，页面上先读到的永远是当前生效的画像。

**悬停承载信息**：三条曾经常驻的信息都并进了按钮的悬停提示，界面因此更安静——

| 按钮 | 悬停内容 |
|---|---|
| 结论上限 | 当前用量 / 上限（手动不计入）、统一与分组两种口径及取较大值、手动条数与不受阻挡 |
| 刷新 | 更新于 … · 数据目录 … · 已刷新 … · 点击重新读取 |
| 反馈与建议 | 未设置时说明缺少 `feedbackUrl` |

`结论上限`、`刷新`、`反馈与建议` 三个按钮统一用 `outline` 变体（同样的描边与圆角），主操作仍是 `primary`。

**条目卡片**：一行只留一个操作入口。

| 元素 | 位置 | 说明 |
|---|---|---|
| `编辑` | 卡片脚注最左（置信度左边）；**与置信度同款胶囊**（999px 圆角、11px 字、1px 8px 内边距），主色填充 + `label-primary-foreground` 白色前景字 | 点开菜单：`编辑文字` / `升为X` / `降为Y` / `废弃`（或 `恢复`）/ `删除`（废弃区内为 `永久删除`，仍需二次确认） |
| 置信度 | 编辑右侧 | 与之前同款配色，低置信度仍是红色 |
| 状态 | 其后 | `生效 / 已废弃 / 已取代`；**首次时间在这一枚的悬停里**（`首次 2026-10-17 10:33`），不再单独占一行 |
| 依据 | 其后 | `依据 · 用户的话` / `模型应答` / `两者合并` |
| 来源 | **紧跟依据**，同一行 | `来源 N 处`，悬停展开会话 · 轮次 · 时间 · 原文；不再单独成行 |

合并后每条结论只剩「一行正文 + 一行元信息 + 一个菜单」，列表不再是按钮阵列。

**路径可移植**：插件目录内**没有任何绝对路径**（`cordis.patch.yml` 的 `dataDir` 留空，代码里也不写死盘符）。数据目录默认是 `<DSH_HOME>/user-portrait`；`DSH_HOME` 未设置时回退 `~/.dsh/user-portrait`。真要换位置，把 `dataDir` 填成相对或绝对路径即可。

**三个提炼入口**：三个按钮长得像但行为不同，区别写在各自的悬停里。

| 按钮 | 做什么 | 不做什么 |
|---|---|---|
| 立即重新提炼 | 用**已提炼的证据**（上次合并后新增的；没有则最近 40 条）重新合并画像 | 不重读会话、不重新摘要 |
| 回填全部历史会话 | 只补**尚未提炼**的会话：跳过子代理，每会话取最近 24 轮，逐轮摘要后写入证据 | 不重复处理已处理/已跳过的会话 |
| 重新提炼全部历史 | 忽略"已处理"与进度水位，重跑所有会话；证据按内容去重 | **不重建画像**——现有结论保留，仍按合并规则叠加 |

三者跑完都自动合并一次，并共同遵守：结论上限（`max(统一, 日常+技术)`，超限先并入相关度 ≥0.5 的同维度结论）、证据黑名单、以及"自动结论 50 字"。

**导出**

- 点「导出」弹窗，五个可选字段全部**默认不勾**：备注、置信度、依据、修改时间、来源。
- **画像维度 + 维度描述 + 结论永远包含**（弹窗里显示为一行锁定的勾选项，不可取消）。
- 只导出 `active` 结论；已废弃 / 已取代 / 已删除属于历史，不进导出。
- 输出为 Markdown，浏览器直接下载 `user-portrait-YYYY-MM-DD.md`。生成逻辑是纯函数（`buildPortraitMarkdown`，挂在模块导出上供离线测试），只有下载这一步依赖 `Blob` / 锚点。

**结论上限**

- 默认 **50 条**，两种模式：**统一**（全画像合计）或 **分组**（日常 20 + 技术 30，合计仍是 50）。两种模式的数字都能自己改。
- **实际生效的上限取两者较大值**：`effective = max(统一总数, 日常上限 + 技术上限)`。把统一数字设小不会让上限低于分组之和，反之亦然；分组模式仍按各自的组上限裁剪。
- 上限存在 `state.json` 的 `entryCap`，面板改完即生效，不用重启。
- **按钮悬停一次性说明全部信息**（页面不再常驻提示行）：
  ```
  当前上限：37/50 条（手动结论不计入）
  统一 50 · 分组 20+30=50（取较大者 50 条）
  手动新增不受上限阻挡，当前另有 4 条手动结论
  ```
  分组模式下第一行改为 `日常 3/20 · 技术 34/30`。
- **手动新增的结论不计入上限，也不会因为超限被并入或删除**。
- **达到上限时**：新结论先在同一维度里找相关度最高的已有结论，**≥ 0.5 就并入**（`entryId` 重新计算，来源合并，置信度取较高且按依据上限夹紧）；**相关度均 < 0.5 时丢弃该结论**，面板顶部显示黄色提示"结论已达上限…请删减后重新提炼"。
- 相关度函数 `similarityScore()` 的取值刻意与现有合并规则对齐：完全相同 1、包含 0.8、共用专有名词 0.6、同对象要求 / 同流程步骤 0.55、其余用字符二元组 Dice。因此**凡是 `isSameConclusion()` 认可的，分数一定 ≥ 0.5**。

**字数上限**

- **可调**：在「结论上限」弹窗里设置 `每条结论字数上限`（1–500，默认 **50**），**自动提炼与手动新增共用同一个值**。存于 `state.json` 的 `entryCap.charLimit`。
- 改动**只约束之后生成或编辑的结论**，已有条目不追溯截断（避免丢字）。
- 越界值自动夹紧（`clampCharLimit`）：`0 → 1`、`9999 → 500`、非数字回退默认值。
- 生效路径：逐轮摘要与回填（`normalizeTurnDigest` 的 `textLimit`）、合并候选与合并结果（`mergeSynthesis` 的 `textLimit` + `combineText`）、超限并入（`enforceEntryCaps` 的 `limits.charLimit`）、手动新增/编辑（`#charLimit()`）。
- 合并两条超长结论时不再直接丢弃新的一条：先保住原句，再把新句的开头塞进剩余空间（`；` 分隔），塞不下才保留更长的一侧。

**证据黑名单**

黑名单是**两半 × 两层**（`blacklist.json`）：

| | 行键（`keys`） | 轮次键（`turns`，`sessionId#turn`） |
|---|---|---|
| 作用 | 精确屏蔽某一行证据 | 整轮屏蔽，**模型改写措辞也拦得住** |
| `pinned*` 层 | 物理删除 / 时间线清理真正删掉的行 | 物理删除与清理中**没有被 active 结论引用**的轮 |
| 派生层 | 非 active 结论所支撑的行 | 非 active 结论引用、且没有 active 结论引用的轮 |

- **为什么要轮次键**：旧实现只按"文本精确"的行键屏蔽。模型重新提炼时改写了措辞，新行的 key 就变了，于是"重新提炼全部历史"能把删掉的结论原样拉回来 —— 这正是之前失效的直接原因。
- **为什么要 pin 轮次**：旧实现只在"真的删掉了行"时才 pin。若账本已被压缩、或按轮次找不到行（实测 54 次 purge 里 53 次删 0 行），删除就**什么都没留下**。现在即使删 0 行，也会把该结论的来源轮次 pin 住。
- **active 豁免（你定的边界）**：同一轮若仍被某个 active 结论引用，**不整轮屏蔽**（只按行屏蔽），避免删一条结论连带毁掉另一条的依据。恢复结论时，它贡献的行键与轮次键一起解除。
- **三条入口都过滤**：逐轮摘要（`#dropBlacklisted`）、回填 / 重新提炼全部历史（同一函数）、合并（`selectSynthesisSource(rows, keys, turns)`）。
- **时间线清理也入黑名单**：`compactTimeline` 删掉的每一行都写进 `pinnedKeys`，整轮被删空的轮次写进 `pinnedTurns`——否则清理本身就是"给重提炼准备素材"。
- **历史回填**：`backfillBlacklistTurns()` 在启动时读 `deleted.log` 的 purge 记录，把这些结论的来源轮次补进 `pinnedTurns`（版本标记 `blacklistTurnBackfillVersion`，只跑一次）。
- **手动结论**：没有 `sources` 时按文本匹配 + 从匹配行反推轮次，再照上面的规则 pin。
- 「证据时间线」页顶部显示 `已屏蔽 N 条证据 · M 轮`；「清空黑名单」只放开 `pinned`（派生层立即重算），「清理时间线」的悬停里写着清理规则。
- **仍存的边界**：轮次键按 `session#turn` 屏蔽，同一轮里若另有**未被任何结论引用**的证据，也会一起被挡；这是"宁可少捞"的取舍。

**清空废弃区**

- 废弃区标题栏有「清空」按钮：**一键物理删除全部非 active 结论**（已废弃 / 已取代 / 已删除），连同只属于它们的证据。
- **二次确认**：第一下只把按钮变成「确认清空？」，5 秒内再点才真正删除，超时自动取消（与单条删除同一套机制）。
- 每条被删的结论都会在 `deleted.log` 写一行，证据行进入 `pinned` 层；废弃区为空时按钮不显示。

**时间线清理**

- 「证据时间线」页有「清理时间线」按钮：**先预览，再删除**。弹窗给出 `将删除 N 条 / 保留 M 条 / 涉及 K 轮`，确认后才动手。
- 归组规则：**同一会话同一轮**（sessionId#turn）算一组（覆盖来源相同）。
- 删除规则：
  - **没有被任何结论引用的轮**（含废弃结论）→ 整轮删除；
  - **被引用的轮** → 最多保留 **2 条**，优先保留真正支撑结论的那条，其次保留较新的；
  - 黑名单里的行若落在未被引用的轮里，也一并删除；`pinned` 层的屏蔽不因此解除。
- 安全阀：删除前把账本备份为 `evidence.jsonl.before-timeline-compaction`，并写一条 `deleted.log`（action=`compactTimeline`，含统计、pin 的键/轮数与备份路径）。
- **与黑名单的关系（已修）**：删掉的每一行都进 `pinnedKeys`，被删空的轮进 `pinnedTurns`（active 结论引用的轮除外）。在此之前清理只删不记，等于把 757 行证据重新交给下一次提炼 —— 实测两次清理删了 605 + 152 行、黑名单却仍是 3 条，就是这个原因。
- 触发时机：只在「回填」「重新提炼全部历史」跑完后**计算预览**（`progress.timelinePlan`），面板显示"本次重跑后可清理 N 条"；删除仍需你确认，不会自动发生。

**反馈与建议**

- 配置项 `feedbackUrl`，默认空。空时按钮**置灰**并提示"未设置反馈网址（配置项 feedbackUrl）"；填上并重启后点击在新标签页打开。

**输入框画像开关**

会话输入框下方、**紧挨「完全权限」**的位置有一个「画像」控件。它注册到同一行的 **list** 槽位 `conversation.input.left`（渲染在权限 + 计划之后），**不动** `conversation.input.permission` —— 那是 **single** 槽位，注册进去会遮蔽权限选择器本身。

- 点开后是一个小浮层：**启用画像**（总开关）+ **日常画像** + **技术画像**（两个分组开关）。总开关关闭时两个分组置灰。
- 悬停即说明：触发按钮为"把画像作为本会话的参考（点击展开开关）"，每个开关各有一行简介。
- **默认关闭**：新会话不再自动注入画像段落，需要时在输入框旁打开。
- **只影响提示词注入**：`portrait_*` 工具仍可读取画像，提炼也照常进行；关掉某一组后，提示里**连该组的条数都不会出现**。
- **按会话持久化**：存在 `state.json` 的 `sessionModes[sessionId]`，切回会话或重启后保持。
- **子代理继承父会话**：子代理没有自己的输入框，读不到自身设置时沿用父会话的开关（自身有显式设置时以自身为准）。
- Host 侧 `?view=sessionMode&session=<id>` 读取，`op: setSessionMode` 写入；提示段落同步读取内存缓存，因此注入判断是同步完成的（不阻塞装配）。

## 9. 已知限制与后续可做

1. **面板视觉需要你确认**：设计规格、令牌、结构断言与图标几何都已核对，但真实浏览器里的观感仍需你看一眼（改动全部在客户端文件里，重载插件即可生效）。
2. **客户端半边改动必须重载插件**：改 `client.js` 后光刷新页面不一定够，最稳的是在插件管理器里重载 user-portrait（Host 半边 `index.js` / `lib/*.js` 的改动则必须重载或重启）。
3. **画像合并按维度分次调用**：日常组一次、每个技术维度一次，未在回复里出现的维度原样保留。
4. **配置表单不可视**：插件的 `Config` 是自实现的 Standard Schema，`Config` 服务把它标为 `unsupported`，因此设置界面不渲染配置表单 —— 配置目前改 `cordis.patch.yml`。若要可视配置，需改为 schemastery（但本包 import 不到）。
5. **profile 补丁里有一行冗余覆盖**：`.dsh/profiles/desktop/cordis.patch.yml` 末尾的 `- id: user-portrait / disabled: false` 是插件管理器写入的，会在每次配置重载时产生 `patch: entry "user-portrait" not found` 告警；不影响加载，可忽略。
6. **历史回填未执行**（按你的选择从新会话开始积累）。需要时用面板按钮或 `portrait_maintain(action:"backfill")`。
7. **子代理生成的会话不会被提炼**：`origin: 'subagent'` 的会话会被跳过，避免把工具噪音当成你的表达。
8. **面板样式与图标是「自持」的**：不依赖任何客户端 UI 包，代价是官方控件升级（圆角、状态色、图标几何）不会自动跟随；升级桌面版后如发现观感偏差，对照第 6 节约束 ④ 重新核对一遍即可。
